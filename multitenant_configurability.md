# Multi-Customer Medallion Refactor (bronze/silver/gold + SQLite→RDS)

## Context

Today the recon engine is single-customer and single-source: HSBC statement PDF + IREPS Bill Status + RNOTE/CRN, parsed straight into in-memory frames, matched, and served from an in-memory run store. The goal is to make it a product usable by many customers with different banks and PO sources:

- **Bronze** = raw uploaded files (registered, hashed, kept on disk).
- **Silver** = each source's parsed output in its own native shape (audit + re-transform).
- **Gold** = one common schema per input kind (bank txns, bills, lineage docs, recoveries) that reconciliation is defined on, regardless of source.
- **Matching rules become per-customer config** ("delta" tolerances: date within N days, amount within ₹X, paid statuses, signal weights).
- **Persistence**: SQLite locally via a single `DATABASE_URL`, swappable to AWS RDS (Postgres) later; schema auto-created on startup.

Decisions locked in with the user:
1. **Incremental strangler** — matcher/engine logic untouched; existing parsers become the first adapters; output stays verifiable against today's results.
2. **Shared DB, `customer_id` on every table**; adapter selection + rule sets are per-customer config rows.
3. **Files on disk, tables in DB** — bronze is a file registry; silver/gold/runs/config are DB tables.
4. **Frontend minimal touch** — existing API contract preserved byte-compatibly.
5. **Incremental runs (added later by user): accumulate + carry forward, locked ledger, as Phase 6.** Files ingest into gold once; a run reconciles new credits against ALL still-open bills; confirmed matches are durable (never rematched); exceptions carry lifecycle status across runs. Phases 0–5 stay snapshot-mode and golden-verifiable; Phase 3's schema is made incremental-ready so Phase 6 needs no rework.

Key constraint: **Python 3.9** (no `X | None` at runtime). SQLAlchemy 2.0.x supports 3.9. All new deps: `sqlalchemy>=2.0,<2.1`, `alembic>=1.13`, dev-only `pytest`.

## Core design decisions

- **Gold in-memory frames keep today's column names** (`zone_guess`, `NetAmt`, `PaymentAdviceDateToBank`, …). The engine, `exception_queue`, `serialize.py`, `report.py`, and the frontend column presets / summary `Category` strings all depend on them. Clean snake_case names live only at the **DB column** level; the rename map is isolated in `db/gold.py`. A canonical rename is a possible later phase.
- **Gold frames flow in memory through the engine; DB writes are side effects** (a `sinks` callback object). A run never depends on DB read-back → stays diff-able against the golden master; CLI stays DB-free.
- **Silver = ONE table with a JSON payload** (`silver_records`), not per-adapter tables — silver schemas churn per new bank; zero migrations per new source. Promote to typed tables later only if silver-level querying is needed.
- **Run frames = JSON rows in `run_frames`** (frames are ~thousands of rows; `serialize.df_to_records()` already handles NaN/NaT/numpy/dict/list columns). Workbook stays a file under `data/runs/{run_id}/`.
- **Money stays Float** for golden parity (Numeric is a flagged RDS-era hardening with golden re-baseline).
- **Alembic migrations from Phase 1** (not bare `create_all`): `alembic init` in Phase 1 with one autogenerated initial revision covering the full schema (all models land in `db/models.py` in Phase 1, even those first *used* in later phases). `init_db()` runs `alembic.command.upgrade(cfg, "head")` programmatically + idempotent seeding on startup — a fresh SQLite file and a blank RDS database initialize identically, and schema changes discovered in later phases become autogenerated revisions instead of drop-and-recreate. `env.py` sets `render_as_batch=True` (SQLite's limited ALTER support) and reads `DATABASE_URL`.
- **Positional-index fix**: matcher's `bill_indices`/`candidate_indices` stay positional in memory (zero matcher changes). Gold bills get app-side uuid `id`s before insert; positions are translated to a `run_match_bills(run_id, match_id, gold_bill_id, role)` link table at persist time. Recoveries' positional `BillIndex` likewise becomes a `gold_bill_id` FK via `row_seq` join in the adapter.
- **Empty-parse hazard fix**: `gold/schemas.py` `ensure_schema(df, frame_name)` reindexes to the declared column list, so an empty HSBC parse yields an empty frame WITH columns.
- **Incremental-readiness baked into Phase 3** (used by Phase 6): gold tables get `UniqueConstraint(bronze_file_id, row_seq, run_id)` (dropping `run_id` from the key is the planned Phase 6 migration), gold rows stay immutable (settlement state lives in the ledger, not as gold mutations), and every gold row carries `customer_id` + natural-key columns so entity-level upsert is possible later. `run_id` on gold becomes nullable in Phase 6 (ingestion-owned rows vs run-owned rows).

## Adapter interface (`recon/sources/base.py`)

```python
class SourceAdapter(ABC):
    source_type: str           # "bank_statement" | "bill_status" | "lineage_rnote" | "lineage_crn"
    adapter_key: str           # "hsbc", "ireps", "ireps_rnote", "ireps_crn"
    file_kinds: Tuple[str, ...]
    def parse(self, path, params) -> SilverResult: ...          # frames: Dict[str, DataFrame], meta
    def to_gold(self, silver, params) -> Dict[str, DataFrame]: ...  # adds row_seq, ensure_schema
    def selfcheck(self, gold, path, params) -> Optional[dict]: ...  # raise SelfCheckError to fail loud
```

- `hsbc_bank`: parse = `parse_hsbc_statement(path, credits_only=False)`; to_gold adds `used_in_recon` (txn_type=="TFR+"); selfcheck = `bank_selfcheck` + existing count/±1 rule, raising `SelfCheckError` (routes map → `BANK_SELFCHECK_FAILED` 422, same wire behavior).
- `ireps_bills`: returns `{"bills", "recoveries"}`; rewrites positional `BillIndex` → bill `row_seq`.
- `ireps_rnote`/`ireps_crn`: wrap `load_rnote`/`load_crn`; `sheet` from `source_configs.params` (finally exposes rnote_sheet/crn_sheet).

Parsers do not move.

## Rules (`recon/rules.py`)

`MatchRuleSet` dataclass: the six current tunables + `paid_statuses` (frozenset, default {"PAYMENT MADE","CO7 DONE"}) + `weights` (default {"advice_date":4, "zone":2, "co7_date":1}). Resolution order: dataclass defaults ← customer's DB rule set ← the six form tunables (form wins; DB supplies what the form can't express).

- **Dead-config fix**: `engine.reconcile()` gains `paid_statuses=None` (defaults to `scoring.PAID_STATUSES`) and passes it to `match_bank_to_billstatus` (which already accepts it). Defaults identical → golden output unchanged.
- `scoring.score_pair` gains optional `weights` defaulting to current module constants; confidence labels stay signal-boolean-derived (weights only affect ranking).

## Pipeline (`recon/pipeline.py`)

`run_pipeline(inputs, adapters, params, rules, sinks=None)`: parse → `sinks.on_silver` → to_gold (+uuid/row_seq) → `sinks.on_gold` → selfcheck (fail loud) → build the frames the engine expects (bank = used_in_recon subset, bank_all, bills, recoveries, rnote/crn) → `engine.reconcile(...)` → today's 12-frame dict. App passes DB sinks; CLI passes none. `engine.run(cfg)` becomes a thin wrapper with HSBC/IREPS adapters, exact same return shape.

**Phase 6 — Incremental runs (accumulate + carry forward, locked ledger)**

*Ingestion becomes idempotent and entity-aware:*
- **File-level dedup**: upload whose sha256 already exists for the customer → reuse its gold rows, skip parsing. Alembic revision drops `run_id` from the gold unique key (`(bronze_file_id, row_seq)` remains) and makes gold `run_id` nullable — gold rows become ingestion-owned, not run-owned.
- **Entity-level upsert for bills** (file dedup is NOT enough here: two daily IREPS exports are different files containing mostly the same bills): natural key `(customer_id, bill_number, co6_no)` identifies a processing attempt; a newer export's row for the same key UPDATES mutable fields (status, co7_no, co7_date, payment_advice_date, amounts) in place rather than inserting a duplicate. Blank/`"-"` bill numbers never merge (mirrors `group_bill_attempts` rules). Recoveries re-linked on upsert.
- **Bank credits**: daily statements are naturally disjoint, but guard anyway with natural key `(customer_id, bank_ref, value_date, amount)` — a re-uploaded overlapping statement upserts instead of duplicating.
- Lineage docs: upsert by `(customer_id, doc_type, doc_no)`.

*Run modes:* `POST /api/runs` gains `mode: Form("snapshot")` — `"snapshot"` = today's behavior (unchanged, golden-verifiable); `"incremental"`:
1. Ingest any uploaded files (dedup/upsert as above).
2. Build the candidate pool from the DB: bank side = new statement's credits PLUS credits from `exception_ledger` still OPEN as BANK_ONLY; bill side = ALL customer bills not consumed by a LOCKED `match_ledger` row and not zero-net.
3. Feed the pool through the UNCHANGED matcher (`match_bank_to_billstatus` just receives different frames — `window_days` is ignored in incremental mode; the open-bills pool replaces the advice-date window).
4. Persist: new matches → `match_ledger` (HIGH confidence auto-LOCKED with `locked_by='AUTO_HIGH'`; review confidences stay OPEN until user accepts); resolved exceptions marked RESOLVED with `resolved_by_run_id`; new exceptions appended OPEN; run payload/frames stored as usual.

*Locked-ledger rule:* a LOCKED match's credit and bills are excluded from every future pool — never rematched. OPEN (review) matches keep their bills claimed within a run (as today) but a user can REJECT them, releasing both sides back into the next run's pool.

*Concurrency & consistency guards (correctness, not optional):*
- **One incremental run per customer at a time**: two concurrent incremental runs would both see the same open pool and double-match. Enforce with a partial unique index `runs(customer_id) WHERE status='running'` (works on both SQLite and Postgres) plus an application-level check returning 409 `RUN_IN_PROGRESS` if an incremental run is already in flight for the customer.
- **Upsert must not mutate bills consumed by a LOCKED match**: a newer export updating `net_amt`/`status` on an already-settled bill would make the ledger reference numbers that no longer exist. On upsert, rows referenced by a LOCKED `match_ledger_bills` entry are skipped and the incoming change recorded as a conflict row (`ingest_conflicts`: gold_bill_id, bronze_file_id, changed_fields JSON, seen_at) surfaced in the run payload — flag, never silently overwrite.

*New additive endpoints:* `POST /api/matches/{match_ledger_id}/accept` and `/reject` (accept → LOCKED `locked_by='USER'`, reject → REJECTED + release); `GET /api/ledger?customer_id=` (durable matches + open exceptions). Frontend untouched this phase beyond optionally surfacing accept/reject on the MATCH_REVIEW queue rows.

*Files:* new `db/ingest.py` (dedup/upsert logic), `recon/pipeline.py` gains `run_incremental(...)` alongside the snapshot path; `routes.py` mode param + ledger endpoints; one alembic revision (gold key change + any ledger tweaks).

Verify: golden STILL green in snapshot mode (the gate never moves). Incremental scenario test: split the sample statement's credits into two synthetic halves, run incremental twice with the same bills export, assert (a) the union of ledger matches equals the snapshot run's matched set, (b) second run ingests the bills file without duplicating gold_bills rows (row count stable), (c) a bill matched in run 1 never reappears in run 2's pool, (d) accepting then rejecting an OPEN match moves both sides out of / back into the pool, (e) a second incremental run started while one is running gets 409 RUN_IN_PROGRESS, (f) re-ingesting a bills export with a changed amount on a LOCKED bill produces an `ingest_conflicts` row and leaves the gold row untouched.

## Schema layout decisions (raised post-implementation, 2026-08-24)

The user asked whether the `bronze_`/`silver_`/`gold_` table-name prefixing is the right design, versus real per-layer namespaces, multiple typed silver tables, and splitting calculated columns (e.g. `gold_bank_txns.used_in_recon`) into side tables. Resolved as follows — revisit only when the stated trigger condition is met:

1. **IMPLEMENTED 2026-08-24 (moved up from RDS cutover — user chose real separation now).** Real per-layer schemas, not a naming convention: every model declares `schema="bronze"|"silver"|"gold"` (app/control-plane tables omit it, landing in the default schema). On Postgres this is a native `CREATE SCHEMA`, one `DATABASE_URL`, one database, real cross-schema joins in a single transaction. On SQLite (no schema concept at all) the same declarations resolve via `ATTACH DATABASE` (`db/base.py: register_sqlite_attach`) — locally each layer is a genuinely separate physical file: `data/app.db` (main, renamed from `recon.db`), `data/bronze.db`, `data/silver.db`, `data/gold.db`, joined on every new connection. Tables dropped their layer prefix since the schema now conveys it (`bronze_files`→`bronze.files`, `gold_bank_txns`→`gold.bank_txns`, etc.). Superseded the originally-sketched `schema_translate_map` approach — the ATTACH mechanism was verified empirically (compiled DDL on both dialects, live SQLite connections) to be simpler and more literal: opening `bronze.db` in a SQLite viewer shows *only* bronze's tables, which is what "separate collection per layer" actually means. Two verified non-obvious behaviors: (a) FK target strings must be schema-qualified whenever the *target* has a named schema — even gold→gold — regardless of the referencing table's own schema; (b) SQLite silently drops FK constraints that cross ATTACHed files (no enforcement loss in practice — no model uses `relationship()`, `PRAGMA foreign_keys` was never set), while Postgres newly *enforces* those same edges — an accepted, documented asymmetry. Local dev DB was reset (test/demo data only, no production customers existed) rather than writing a data-preserving cross-dialect migration.
2. **Silver stays one JSON table (`silver_records`), not one typed table per source.** Silver's shape churns with every new bank/PO adapter; one JSON table means zero migrations per new source, which is the entire point of the adapter pattern. Nothing queries silver by column today — it exists for audit and re-transform, and both read whole rows. **Trigger to act:** the first real requirement to run SQL over one source's raw silver rows — promote *that source* to a typed table (additive), or add a SQL view over the JSON (`json_extract(payload,'$.amount')`) as a lighter middle step that works on both SQLite and Postgres/JSONB.
3. **`used_in_recon` stays a gold column, not a side table.** The general principle — computed/rule-dependent values don't belong in immutable gold facts — is already enforced everywhere it matters: settlement lives in `match_ledger`, exceptions in `exception_ledger`, per-run output in `run_frames`/`run_match_bills`, none of it as gold mutations. `used_in_recon`, though, is a **deterministic, row-wise classification** (`txn_type == "TFR+"`) that depends only on the row itself, not on matching rules or other rows — that's exactly what a source adapter's silver→gold transform is for, and every future bank adapter answers the same question in its own dialect. The real dividing line is *row-wise deterministic → gold column* vs. *rule-dependent or cross-entity → computed at run time / stored in state* — the contrasting case is bill eligibility (`Status IN paid_statuses`), which is genuinely rule-dependent (customer-configurable) and is therefore NOT stored in gold; the matcher computes it from `MatchRuleSet` at run time. **Trigger to act:** `used_in_recon` becoming itself customer-configurable (e.g. "also include reversals") — at that point it crosses the line and should move to runtime evaluation exactly like `paid_statuses`.

## Risks / flagged follow-ons (not in this phase)

1. Money as Float (Numeric = RDS-era hardening + golden re-baseline).
2. Alembic autogenerate output must be reviewed per revision; non-additive SQLite migrations rely on batch mode (`render_as_batch=True`), set in env.py from the start.
3. Gold rows are per-run during Phases 3–5 (same file twice → duplicate rows under different run_ids); RESOLVED by Phase 6's dedup/upsert ingestion — accepted as transitional state until then.
4. Confidence labels stay signal-based; per-customer label thresholds = follow-on design.
5. SQLite + threadpool: `check_same_thread=False`, session-per-request, single-worker uvicorn documented.
6. Retention counts for `data/runs/` and `data/bronze/` to confirm with user.
